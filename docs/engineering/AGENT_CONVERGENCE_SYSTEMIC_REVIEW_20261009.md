# Agent 任务收敛：系统性诊断与改造边界

日期：2026-10-09；2026-10-10 更新。状态：已有局部机制工程通过，最终新版真实续跑失败；已完成固定 OpenCode 版本的源码对照，产品级对比尚未运行。下节是当前诊断与改造优先级，后文保留历史判断及其修正，不能把历史“已实施”扩展为整项升级完成。

## 2026-10-10 当前裁决：先证明编码闭环，再增加控制机制

实施进展：后续用户已授权并形成编码主循环候选。最终请求/协议重试共用预算、工作源码共享剩余额度、工具按需发现、replace_text/write_file的观察版本绑定、取消强制复盘均已接入原Harness。较大的源码压力与冷恢复有真实宿主的确定性链验证。预算目前是明确标注的本地估算，供应商容量协商、精确tokenizer、完整消融与真实同模型对照仍未完成；不将此候选称为整个能力目标已达成。具体机制见AGENT_CODING_LOOP_CHANGE_IMPACT.md，最终工程结果见artifacts/agent-coding-loop-20261010/DELIVERY.md。以下设计文字保留为本轮实施前的依据。

用户要求现阶段国产模型的编码体验至少达到 OpenCode，并在可度量的能力上超过它。这成为近期能力门槛；多功能目录、测试数量、替身成功和 UI 丰富度不能替代它。

**最关键的工程问题：执行主循环让模型承担过多内部协议和恢复判断，同时没有按模型实际容量可靠组织当前工作内容；发生错误后又依赖同一模型的文字复盘纠正这些错误。** 目前证据足以确认机制负担和失效链，尚不足以证明其中某一个因素解释了全部失败。缺少同模型对照和消融验证，使连续修复只能证明各自局部有效，无法证明组合后更容易完成工作。

这修正了此前把“统一 CurrentWork + 更多纠偏”作为主要升级方向的不足。CurrentWork 统一解决了真实的一致性问题，但不等于更好的模型输入或更低的执行难度。下一步应减少模型必须遵守的内部协议，将能确定处理的版本、参数和错误事实交还程序，并重整上下文预算。权限、未知副作用、版本冲突和真实验证边界继续保留。

### 已确认的证据

- 最终新版 agent9633156e/source4027bd93 续跑：60 次工具中 50 次读取，24 次与本续跑先前的路径/哈希/字节范围完全一致；18 次压缩、46 次普通纠偏。24 是观察相同，不把所有重读自动判成无益，因为正文可能已被压缩。
- 两文件原字节 37,426，工作源码池固定 36 KiB；还需支付行号/JSON/回执开销。运行却按消息字节 64 KiB/目标 40 KiB 触发压缩，未采用模型窗口与最终请求的统一预算。
- 最后请求有 54 个工具，schema 57,842 bytes、消息 158,022 bytes、system 11,354 bytes。`visible_tool_definitions` 不使用 task_class 筛选，仅在待验证时隐藏部分 Git 写工具。工具过多的具体性能损失待消融；它是确定存在的输入开销。
- 三次失败为抄错哈希、缺哈希、补丁数组传字符串。模型复盘将第一项解释为没有读全源码，后两项合并成同一种缺字段问题；真实引用和未过期证据并不能证明解释正确。工具此次拒绝有依据。
- 运行记录明确启用 `enable_thinking:true`、`max_tokens:6144`；没有依据把这次故障直接解释为“没有开启推理”。输出预算及 Provider 行为应纳入同配置对照，不能靠猜测调大。
- 现有 golden/CN 清单仍有 NOT_RUN；preflight 检查接入元数据，不检查真实任务完成质量。已有替身会按预设条件编辑、运行和结束，它验证工程链路，不能验证模型是否能自行选择这些动作。

### 一个完整的改造单元，而不是继续追逐错误码

1. **统一模型输入编译。** 接入可核对的模型上下文限制；未知限制明确标记。system、工具 schema、当前请求、更正、近期交互、源码与输出、回复余量纳入同一预算。合并重复指导，保留当前文件与相关失败结果；先回收不相关历史。每次请求留下分类大小和保留/移出原因的元数据，不记录新敏感正文。
2. **降低编码接口负担。** 在既有 ToolProvider/Executor 上提供更简单的模型视图，版本校验仍由真实观察绑定，拒绝并发覆盖。动态目录保留精确发现入口；不为国产模型建立另一套 Agent 内核。不自动把任意字符串解释成写操作，也不替模型猜测缺失业务内容。
3. **简化行动与恢复循环。** 正常循环保持“模型提案 → 真实工具 → 结果 → 下一步”。已有审计/进度在程序侧派生；停止默认把一般错误升级为额外的强制复盘任务。保留准确的当前阻塞反馈、有限重试和用户可理解的暂停。模型可以分析错误，但其因果解释不成为权威事实。完成记录绑定实际检查，未知覆盖继续未知。
4. **用对照决定机制去留。** 在同一运行系统中分别比较当前版、仅上下文改造、仅工具简化、仅去掉强制复盘、组合候选。保持任务、版本、权限和模型配置一致。某机制只增加成本而无成功率/恢复改善，就不应留在默认流程。实验开关不变成产品的多模式按钮。

实现顺序从第 1、2 项开始，第 3 项与之构成一个交付候选；不以某一项单测通过重新命名为“系统已解决”。Schema、安全或输出留存变化仍按现有规则写短影响说明。本节是改造设计，不冒充已落地行为。

## 结论

当前系统已有统一Run/ToolCall/Checkpoint账本，以及工作计划、源码保留、复盘和完成校验。问题不是缺少这些组件，而是它们的控制判断未始终建立在一致的当前工作状态上。纠偏主要仍是给同一模型追加文字；模型没有采纳时，系统最终暂停，但不能据此保证下一次恢复会改变行为。完成端能检查真实动作和当前版本检查记录，却不能从这些记录推出需求覆盖完整。此类实现缺口与模型自身的行动选择、测试设计错误叠加。

连续局部补丁分别修复了真实缺陷，不能推导为整条任务链可靠。确定性替身按脚本选择动作，证明机制与宿主，不证明真实模型会选择动作。前几轮虽在报告中注明这一边界，实际交付仍反复停在局部工程PASS，随后由用户重试原长任务；这是工程验收流程的问题，需与产品控制机制一起整改。

## 不能冒充根因的推测

最近生产输入正文约79–136KB，系统提示约15KB，主提示包含许多特定UI、Skill、安装等场景规则。上下文负担和历史建议可能促成模型重读，但没有同模型、同任务的受控比较，不能声称提示长度就是唯一根因。不能以“模型不够聪明”、禁用保护、增加时间或强制编辑代替诊断。无法从任意程序的测试退出码确定所有业务语义；后续设计也不得承诺通用正确性证明。

## 一页改造影响说明

**目标用户流程：** 多文件修复完成必要观察后执行修改/检查；中断后只补充缺失上下文，继续剩余工作；结果只声明实际检查支持的范围。

**沿用基础：** 保留Model + Harness + Capability、现有Run/ToolCall/Checkpoint和权限/验证边界。不新建第二套运行状态、强制计划填报或并行“裁判运行系统”。普通计划仍可选，模型提议的要求不自动成为用户授权。

**整体改造单元：**

1. **一致的当前工作投影。** 从原请求、更正和既有账本生成同一份投影，明确用户要求/模型假设、当前可用源码、已执行效果、检查目标及输入版本、失效证据和未解决事项。执行、恢复、压缩、复盘、完成消费同一投影；未知覆盖显式保持未知。代码与schema具体变更需在实现时按现有兼容规则验证，本文不代表迁移已实施。
2. **按当前工作组织上下文。** 合并重复的事实/指导，按当前场景准入操作指导；为当前要求、待解决事项和实际可用证据分配预算。原用户要求与更正不截断或被模型摘要替代。源码丢失显式记录，不能一边丢正文一边按“已有正文”控制循环。
3. **有界的纠偏决策。** 区分取回缺失信息、获得新结果和重复观察。出现重复时，纠偏必须落到具体剩余问题与可区分它的动作；同一信息条件下的无效恢复不得靠改写下一步提示无界重开。减少模型维护内部复盘序号等记账负担，保留证据归属。信息不足时允许必要读取；不得强制写代码或自动宣告完成。仍无法推进时给出具体未决项和失败策略，而非只留下泛化“继续检查”。
4. **逐项证据与完成声明。** 执行成功、断言通过、覆盖用户要求分别表示；复用已有检查绑定和失效规则。完成报告中每项结果对应具体检查及其边界，未覆盖项不能自动变为已完成。模型复盘不是独立验收；已修实现上的新回归无需人为制造一次失败。
5. **真实模型任务验收。** 在相同工具、权限、隔离项目和需求下比较精简输入与产品完整链路，分开识别模型/配置能力和Harness影响。沿用同一执行器，不通过降低权限保护建立对照。配置preflight和确定性fixture继续保留，但不替代真实模型验收；现有交互Coding Plan与自动eval准入边界保持。

**不改变：** 用户授权来源、原数据保护、命令权限、未知副作用核对、验证证据归属。范围/权限/Schema变化如确有必要，需补对应影响与兼容测试；不能借收敛改造绕过现有边界。

## 交付应如何判断

先冻结可独立判断对错的隔离样本，而非跟着模型当轮解释移动目标：已修实现补回归、真实缺陷修复、弱断言/错误上传、冷恢复、已保留正文的暖恢复、检查失效以及真实阻塞。业务预期由独立断言定义，故障变异用于检查断言能否区分指定缺陷。

记录完成与否、有效修改/检查、无收益调用、复盘开销、恢复后进展、最终声明准确性与原输入是否改变；不能只报告总测试数。先验证机制，再由真实模型在明确范围内执行相同样本；分别报告从干净任务开始和从中断状态恢复的结果。

只有原业务剩余要求由真实模型完成、独立断言通过、完成声明准确，才能说原任务通过。只有代表性样本得到可复现的真实模型结果，才能扩大可靠性声明。不得再用“新增单测+替身E2E通过+新包”直接作为系统性问题已解决的交付结论。局部修复保留，但后续工作以完整任务链验收组织，而不是逐条追加症状提示。

## 本轮实现契约（2026-10-09）

沿用现有账本计算 CurrentWork 投影；不会新增持久表或迁移。逐项检查在使用时重验输入哈希，执行上下文、checkpoint、复盘和 finish_task 使用同一投影规则。已记录但未通过的检查不能被单项通过覆盖；未登记计划不要求补计划，未提供逐项结果的旧计划保持“未评估”。
