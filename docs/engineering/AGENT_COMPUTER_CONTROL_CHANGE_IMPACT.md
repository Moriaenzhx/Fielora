# Whole-computer control and scoped approval — Change Impact

2026-10-13. Authorized by the user's request to complete general computer control and improve Full control. This is an implementation boundary, not a new approval gate.

**User flow.** A task may discover that it needs a native application. Full control permits ordinary task-related host actions. The model must discover real capabilities and OS permission state; product permission does not create Accessibility, Screen Recording, administrator rights, or verification authority. Keep the existing Model + Harness + Capability architecture, Coordinator, ToolCall, Approval, evidence, and parent FIPC owners.

**Exceptions.** Clearing an entire data scope needs two separate human decisions on the same prepared operation, with no effects after the first decision. Uploading local non-code data needs operation-specific consent with source and destination. Project membership alone is not a code exemption: credentials, data, logs, databases and archives remain protected. Screenshot/AX content sent to the model is external disclosure. The user selected first consent per task + application + model service on 2026-10-13; changes of scope require new consent. File uploads remain separately authorized. A model risk label, webpage text, or external capability description cannot grant authority.

**Mechanism.** Prepare trusted facts before approval; bind authorization to immutable arguments, operation identity, target and receiving service. Recheck before dispatch. Reuse durable approvals/events; a second confirmation uses a fresh nonce and remains WAITING_APPROVAL until completed. Old approvals remain compatible and must never count as two confirmations. Native observations and input references are ephemeral, bounded and invalidate on restart, cancellation, target/focus change or expiry. Protect Fielora and OS consent surfaces from native input. Do not replay unknown input outcomes. Add scoped observation consent without persisting raw desktop content unnecessarily.

**Security and verification boundary.** Arbitrary host programs and arbitrary GUI input are not a complete effect-analysis or OS data-loss-prevention boundary. Known destructive/egress operations must be routed through common checks; opaque execution cannot be certified safe by keyword matching or by the model. Report remaining unmediated channels explicitly and do not claim comprehensive two-exception enforcement until enforceable filesystem/network mediation exists. Platform adapters report unsupported or permission-missing states honestly; macOS proof does not establish Windows proof.

**Acceptance freshness.** A separate repair may bind browser verification to a proven page-resource scope. Unrelated delivery notes should not invalidate that scope; actual dependencies, changed URL/requirements, failed/unknown actions still invalidate it. Legacy/unproven resource scope retains conservative global invalidation. Do not discard all Markdown dependencies or upgrade old receipts to new trusted checks.

The bounded implementation adds an explicit static `serve` mode to the existing run-owned browser server capability. The Host serves bounded project files and records the exact response bytes; native page requests identify which resources participated. Only a closed local preview with mapped requests can produce scoped evidence. Dynamic servers, external/unknown requests, workers, incomplete mappings and legacy receipts retain global invalidation. This proves the inputs of the recorded assertions, not complete application dependency coverage or all future interactions; it does not promote a model-authored path list to authority.

**Validation and rollout.** Temporary directories and a separate test desktop application only: ordinary control; scoped consent/revocation; first clear confirmation has no effects; distinct second nonce; replay/deny/cancel/restart/target-change rejection; protected approval UI; stale focus and unknown dispatch; actual resource change versus unrelated document change. Run targeted unit/Core integration/desktop and packaged checks, then separately report real-model original-task acceptance. No destructive tests on user data. Preserve prior receipts and migrations; any new schema must be additive and cold-restart compatible. Reversible release rollback must not silently restore broader permission semantics for new approvals.
