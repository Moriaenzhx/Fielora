# Computer control and permission

2026-10-13 implementation contract. This refines Full control within the existing Model + Harness + Capability architecture; it does not add a second permission or execution system.

## User flow

The Agent can discover `computer`, inspect actual platform readiness, select a running application, and perform task-related native operations. Full control allows ordinary actions without a confirmation for each click. OS Accessibility, screen access, administrator rights and application authentication remain separate prerequisites, reported from actual tool facts.

Two human decisions are required before clearing a whole data scope. The first confirms the prepared scope and performs no deletion. The second uses a new nonce and confirms execution of the same unchanged operation. Rejecting or cancelling either stage stops execution. Changed arguments, files or destination invalidate the prepared authorization.

Uploading non-code local data requires a separate, operation-specific approval. Being inside a project directory does not make data source code. Source exemption is conservative: tracked source/configuration, bounded readable content and sensitive-path/content exclusions; it is not a comprehensive secret detector. Files, archives, form values, queries, clipboard data and app observations can all disclose local information; changing the transport does not change the authorization requirement.

The user selected first observation consent per task + application + receiving model service. The approval identifies the application and receiving service. It covers bounded app observation for this task, not file upload, clearing data or another receiving service. Ending/cancelling the task ends its scope. A changed receiver cannot silently receive earlier application observations. Fine-grained revoke UI is not yet implemented.

## Implemented native adapter

The macOS adapter uses real AX/CGEvent operations: status, observe, activate, click, Unicode type, press, scroll, move and drag; screenshot adds exact-window images through ScreenCaptureKit on macOS 14+. Status and target preparation inspect application identities only. The first content observation follows the ordinary persisted approval flow. Native input requires the exact prepared application launch, a fresh snapshot, a valid target and current focus; it cannot auto-click Fielora or OS approval surfaces. Known terminal/script applications and known bulk-clear/upload controls are directed to governed operations instead of bypassing policy.

The model-facing native adapter exposes bounded accessibility text and, after separate WINDOW_IMAGE consent, one ephemeral screenshot of the authorized window. The local UI preview described below remains a separate read-only presentation path and never silently sends pixels to a model. Windows native input is explicitly unsupported in this slice. No desktop screenshot is labelled as Browser evidence. Raw AX element trees and screenshot bytes are not stored in the durable ToolCall receipt: it keeps identity, result metadata, counts and content digests; immediate model context receives the admitted observation. This is not a promise that model replies or submitted tool arguments contain no user data.

Input dispatch is separate from successful task outcome. After unknown/partial input the task must inspect state, never blindly replay. Snapshots are ephemeral and expire; cold continuation observes again. One adapter lock serializes native actions. The existing task Stop action owns cancellation; old execution cleanup must not remove a newer continuation's cancellation handle.

On macOS the CLI Core checks into the Process Manager before querying the current foreground application through system-wide AX. This identity-only call does not activate an app or grant permission. The deprecated public API remains a compatibility maintenance point. AX reads distinguish an absent focused window from a system error; only bounded, identity-checked reads retry a transient CannotComplete result. Native input never retries automatically after dispatch.

## Enforcement boundary

Core prepares trusted facts, routes exceptions through existing Approval and rechecks them before dispatch. Private policy metadata supplied by the model is discarded. Recognized direct clears/uploads and explicit opaque variants receive bounded preparation, approval or a zero-dispatch denial requiring a reviewable operation. The two confirmation stages reuse one approval row with durable events and nonce rotation; no schema migration is required.

This is **not** an OS-wide data-loss-prevention system. Full control still includes arbitrary host programs and configured MCP servers; static argument inspection cannot prove all effects of those programs, arbitrary GUI actions or a series of small mutations. Known route checks and model instructions must not be advertised as complete filesystem/network mediation. These unmediated channels, full desktop screenshots and Windows acceptance remain separate implementation/validation work.

## Acceptance

Use independent temporary data, a local upload receiver and a separate native target application. Prove first confirmation has zero effects, second confirmation survives restart, denied/cancelled/replayed/changed operations do not execute, upload sends no bytes before consent, and actual native Unicode input reaches a saved file. Desktop tests may control the isolated Fielora shell to act as the human, but must not use DOM automation on the native target. Report deterministic-model engineering, packaged host, real model and original user task separately.

For static webpage acceptance, `browser_server serve` can attach Host-observed resource hashes to browser checks. Actual HTML/JS/CSS/Markdown dependencies invalidate checks when changed; unrelated delivery notes do not. Dynamic servers, legacy receipts and unproven request ownership retain global invalidation. This is evidence for the resources exercised by the recorded checks, not automatic proof of complete application behavior.

Completion submission uses that same resource freshness function for declared browser evidence; it does not reintroduce a global-revision requirement after unrelated notes change. Command checks and legacy browser receipts retain their existing global boundary. Diagnostic errors identify the failed requirement and invalid receipt IDs without fabricating replacements or proving semantic coverage.

The visible conversation owns its composer and foreground projection. Switching conversations releases only those UI references, while Core retains background runs. Late callbacks must match the selected conversation generation; a send acknowledgement consumes only the draft snapshot actually submitted.

## Application attribution and local window preview — 2026-10-13

Conversation activity derives the application name and identity from an actual `computer` receipt's `target`, never model prose, proposed arguments or the application list returned by `status`. Failed, denied, cancelled, unknown and missing historical results remain distinct. File edits and commands keep their own categories in mixed groups; an application label does not claim that the application performed those operations. A missing local icon uses a neutral application icon without contacting an external service.

After a successful native application operation, the current active task can show a compact floating window snapshot. A new eligible `computer` receipt or the user's refresh action requests a new capture; this is not continuous video. The user can minimize, reopen or close the preview. Changing conversations or pausing/ending the task removes the active preview, without stopping another background task. The frame records its capture time and is not a historical screenshot of the earlier tool action.

On macOS 14 or later, the existing platform adapter obtains a bounded PNG through public ScreenCaptureKit single-window capture, subject to real system screen-recording permission. The trusted UI supplies only Run/ToolCall IDs and a capture flag. Core resolves the successful owned receipt and the live application snapshot, including launch and window identity. Missing, expired, changed or ambiguous targets return an unavailable reason; another window or the entire desktop cannot substitute. Unsupported platforms/OS versions remain explicit. Icon lookup and pixel capture are read-only; they cannot activate an application or dispatch input.

Local preview image bytes exist only in the ephemeral local query and visible UI. They are not sent to the model, written to files, added to ToolCall receipts, ScreenshotEvidence or diagnostic logs, or treated as verification. Existing application-observation approval and Run/session ownership remain authoritative; this introduces no new approval, Run, schema or evidence system. The separately authorized model screenshot extension is specified below.

Engineering Cross and isolated development/packaged native-window acceptance passed: actual pixels/icon, UI controls, 900×640 layout, snapshot/Run rejection, no model or durable image data, and a real capture settling after Stop with no pixels. Capture uses a short-lived read-only ticket outside the session lock, then revalidates snapshot and cancellation; empty/ambiguous titles fail closed and one native lease covers enumeration through capture. Barrier tests cover concurrent invalidation; real OS ambiguity and permanently missing callbacks were reviewed but not reproduced. Full PreMerge remains failed at the existing Browse close-page target-count assertion. No real-model preview task or normally launched production permission acceptance is claimed; Windows remains unsupported. Scope and retention rules: [Application preview change impact](../engineering/AGENT_APPLICATION_PREVIEW_CHANGE_IMPACT.md).

## Model window images and visible native operation — 2026-10-14

The explicit `computer.screenshot` action asks for WINDOW_IMAGE consent under the existing COMPUTER_OBSERVATION approval, bound to task, actual application launch and actual receiving model/provider/endpoint. It includes both window pixels and bounded accessibility text. Existing text-only grants do not authorize images; an image grant can cover text for the same scope. Recheck the receiver against the actual prepared invocation before capture/send, including edits made while the task is running. Model vision support is not guessed from model names; an adapter image rejection remains an explicit failure and never silently becomes text-only success.

Only the exact authorized window is captured, at most 1280×960 and 4 MiB PNG. Capture runs outside the session lock and revalidates cancellation, window and snapshot before admission. Pixels are removed from the tool result before persistence, then supplied as one ephemeral image message after the complete tool-result batch. Receipts retain digest, dimensions, timestamp and `PREPARED_FOR_NEXT_MODEL_REQUEST`, which does not prove delivery or model understanding. A later computer observation/action replaces or clears that image; pause/restart require recapture. No screenshots are saved to conversation history, checkpoints, files, diagnostics or verification evidence.

Capability support and a response's image attachment are distinct: `status.screenshots` reports platform support alongside actual OS permissions, while `image_attached` describes the immediate response. A status query never attaches an image and must not claim that capture is unavailable for that reason. The legacy `screenshot_available` attachment flag is confined to screenshot-action receipts for the existing visual-context admission path. Durable history sets `image_attached=false` and explains that a new authorized capture is required; saved metadata is not a retained image.

The model capture and optional local preview share one native capture lease. A pending model capture makes new local previews yield, and waits at most 3.5 seconds for an already-running preview without holding the session lock. Only native BUSY before SDK dispatch permits reacquisition; a timed-out capture or dispatched input is never replayed. Native enumeration and capture each retain their separate 1.5-second bounds. Cancellation is checked during lease waiting and after capture; late callbacks retain the lease until finished and their images cannot revive a cancelled task.

Visual input uses integer pixels in the returned screenshot, mapped by host-owned full-window geometry to native screen points. Every input consumes its visual snapshot; the model must obtain another screenshot before another coordinate action or ref-free keyboard action. Inputs recheck current launch, foreground window, geometry, snapshot age, AX state and actual native hit target. Move, click/double-click, scroll and drag can operate a canvas without an accessibility label. Known secure fields and protected/governed surfaces remain refused; a truncated AX tree cannot establish absence of sensitive content. Partly offscreen captures retain whole-window geometry, but native input outside an actual display is denied. Drag releases the mouse on cancellation/error; already-dispatched unknown effects are never replayed automatically.

The local conversation preview shows current window capture time and actual operation feedback. A temporary desktop pointer marks an actual successful dispatched coordinate action, including the final drag location; it is not a live replay of the whole pointer path. A separate non-activating status pill identifies the app/action and exposes the existing Stop command while other apps are foreground. Feedback expires during quiet model work and clears on pause/stop/terminal state. Before each native operation, Core requests Main to hide all feedback windows and waits for a bounded acknowledgement; overlapping operations remain suppressed until all have settled, preventing a second task's busy/failure feedback from covering an active target. The handshake reuses the existing host completion channel and never grants execution authority.
